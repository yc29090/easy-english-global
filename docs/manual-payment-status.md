## 发布策略

本次只部署关闭人工支付的代码。`MANUAL_PAYMENT_ENABLED=false` 是默认值且在 Blueprint 显式设置。创建订单、申报付款、管理员批准均受服务器控制；普通用户申报不能开通会员。批准需要管理员明确 `verified=true`。原生产 mock checkout 仍禁用。

只有实际收款码及归属核验、发件授权、真实 Gmail 到达和安全验收全部完成，才允许设置 `MANUAL_PAYMENT_ACCEPTANCE_VERIFIED=true`，并另外启用 `MANUAL_PAYMENT_ENABLED=true`。这些变量是运维验收声明，不是自动核验或送达证明。当前不具备上述证据，不得启用。

## 修复

- 004 迁移支持重复执行；005 分离历史模拟订单和人工订单的唯一索引，覆盖 pending 和 payment_claimed。遇到历史重复活动订单时整体回滚，保留原数据，不自动删除或拒绝订单。
- 创建订单先锁用户并重新检查状态；唯一索引兜底。审核使用事务锁，重复确认只记一次审计，审计包括完整订单号；拒绝禁用账号、管理员账号和重复升级。
- 邮件任务与付款申报同事务保存；发送失败保留订单和失败状态，管理员可重试，发送中的任务超过两分钟可恢复。邮件采用至少一次语义，进程在服务商接受后、记录成功前崩溃时可能重复提醒。`sent` 仅表示服务商接受，不代表 Gmail 已到达。
- 邮件禁用不会被记为发送成功；SMTP 检查接受结果，邮件正文使用真实换行。
- 管理员后台显示邮件状态并可重试；订单显示完整编号便于人工核对。
